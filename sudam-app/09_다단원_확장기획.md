# 수담(數談) 다단원 확장 기획안

> 기준 문서: `수담 앱 명세.md` (단일 기준 명세). 이 문서는 명세 9장 '확장 로드맵'을 구체화한 **사용 범위 확장 기획**임.
> 현재 상태: 6학년 '비와 비율' 단원 30문항(8범주) 내장. 학운위 승인으로 AI(교사 백엔드 경유) 병행 사용 가능.

---

## 1. 확장 원칙 — 무엇이 바뀌고 무엇이 바뀌지 않는가

**바뀌지 않는 것 (하드 제약 그대로 유지):**
- 반박 태그 근거 필수 입력 (앱의 심장)
- 정답·채점 미제공, 학생 개인정보 제로(출석번호+별명), localStorage 금지, 오프라인 완주
- TORON 5단계 순환 구조와 근거 태그 8종

**바뀌는 것:**
- 발문 은행이 '비와 비율' 전용 → **단원별 발문 팩(pack)** 구조로 일반화
- 범주 칩이 하드코딩 8종 → 팩이 선언한 범주를 동적으로 표시

핵심 통찰: 수담은 원래 '비와 비율' 앱이 아니라 **"대립하는 두 주장이 성립하는 발문"이면 어디든 도는 담화 엔진**임. 명세 6장의 문항 스키마(발문·토론포인트·예상주장 2종·폴백카드 2종)는 이미 단원 중립적이므로, 확장의 본질은 코드가 아니라 **발문 팩의 품질**임.

## 2. 발문 팩(JSON) 구조 — 스키마 확장

기존 문항 스키마는 그대로 두고, 팩 메타데이터를 감싸는 한 겹만 추가함.

```json
{
  "packId": "G6-RATIO",
  "packName": "6학년 · 비와 비율",
  "targetGrade": "초등학교 6학년",
  "achievementStandards": ["[6수02-02]", "[6수02-03]"],
  "categories": {
    "MIX": "농도", "PRICE": "가격", "SPEED": "속력", "RATIO": "비의 기준",
    "RATE": "성공률", "SCALE": "확대·축척", "DENSITY": "밀도", "PERCENT": "백분율"
  },
  "consensusMode": "합의",
  "items": [ /* 기존 30문항 스키마 그대로 */ ]
}
```

- `categories`: 팩이 자기 범주(코드→라벨)를 선언 → 범주 칩이 자동 생성됨. STU·TCH는 런타임 공통 범주로 유지.
- `consensusMode`: O단계 제목("합의" / "쟁점 정리") — 명세 9장 4항(사회과)의 근거를 미리 심어 둠.
- `answerProvided: false` 규칙은 팩 검증 시에도 그대로 강제함.

## 3. 단원 적합성 기준 — 아무 단원이나 되지 않음

토론 발문이 성립하려면 다음 3조건이 필요함. 팩 제작 전에 이 기준으로 단원을 선별함.

1. **대립 가능성**: 직관적 오개념 주장과 수학적 주장이 자연스럽게 맞서는가
2. **근거 다양성**: 식(🔢)·그림(🖼)·기준(⚖)·반례(❗) 등 여러 방식의 논증이 가능한가
3. **반례 생산성**: "숫자를 바꾸면 주장이 무너지는" 반례를 학생이 만들 수 있는가

### 6학년 단원별 적합성 평가 (2022 개정 기준)

| 단원 | 적합성 | 대립 축 예시 |
|---|---|---|
| 비와 비율 (현재) | ●●● | 절대량 vs 비율 |
| 분수의 나눗셈 | ●●● | "나누면 작아진다" 오개념 vs 몫이 커지는 경우 |
| 소수의 나눗셈 | ●●○ | 어림 vs 정확한 계산, 몫과 나머지 해석 |
| 비례식과 비례배분 (6-2) | ●●● | 균등 분배 vs 비례 분배의 공정성 |
| 원의 넓이 | ●●○ | 어림 방법의 타당성(둘레 기반 vs 격자 기반) |
| 자료와 가능성(평균) | ●●● | 평균 vs 최빈값·범위 — "어느 모둠이 잘했나" |
| 공간과 입체 | ●○○ | 대립 주장 구성 어려움 — 후순위 |

**권장 제작 순서**: ① 분수의 나눗셈 ② 자료와 가능성(평균) ③ 비례식과 비례배분. 셋 다 "계산은 되는데 판단이 갈리는" 발문을 만들기 쉬움.

### 팩 제작 절차 (명세 6장 3단계의 팩 단위 버전)

문항당: ①발문·토론 포인트 → ②예상 주장 2종(하나는 그럴듯한 오개념) → ③폴백 카드 2종(반례 유도 질문).
분량: 단원당 12~30문항, 범주 3~8개. 시작은 12문항(범주 3개 × 4문항)으로 충분함 — 한 차시에 쓰는 발문은 1~2개임.

**예시 — 분수의 나눗셈 팩 문항 1개:**

```json
{
  "id": "FD-01",
  "category": "QUOTIENT",
  "question": "리본 3m를 한 사람에게 3/4m씩 나누어 주려고 한다. 몇 명에게 줄 수 있을까? 나눗셈을 했는데 답(4명)이 3보다 커졌다. 계산이 잘못된 걸까?",
  "discussionPoint": "'나누면 작아진다' 직관과 1보다 작은 수로 나눌 때 몫이 커지는 현상의 대립",
  "expectedClaims": ["나눗셈인데 커졌으니 계산이 틀렸다", "3/4m씩 묶어 세는 것이므로 몫이 커지는 게 맞다"],
  "fallbackProbes": [
    { "order": 1, "text": "3 ÷ 1/2 을 그림으로 그려 보면 몇 묶음이 나올까? 나눗셈은 항상 답을 작게 만들까?" },
    { "order": 2, "text": "3 ÷ 3(3m를 3m씩)이면 1명. 나누는 수가 3에서 3/4으로 작아지면 답은 어떻게 변할까?" }
  ],
  "display": { "stage": "R", "cardType": "probe", "answerProvided": false }
}
```

## 4. 앱 수정 로드맵 — 3단계

### 1단계 — 지금 당장, 코드 수정 없음 (수동 팩 교체)
`05_발문은행_폴백카드.json` 내용을 새 단원 문항으로 교체하고 앱 인라인 BANK_SEED를 갱신함. 단원당 HTML 사본 1개(예: `수담_분수나눗셈.html`)를 만들어 두면 교체 없이 병행 사용 가능.
- 장점: 위험 제로, 오늘부터 가능. 단점: 파일이 단원 수만큼 늘어남.

### 2단계 — 팩 선택 UI (본 기획의 핵심, 다음 개발 사이클)
단일 HTML 안에 팩 여러 개를 인라인 내장하고, 시작 화면에서 **단원 팩 선택** 후 발문 목록으로 진입함.

- 시작 화면: 제목·대상학년 표기 아래 팩 카드(팩 이름·성취기준·문항 수) 나열. 표기 문구는 선택된 팩의 `targetGrade`를 따라감.
- 발문 목록: 헤더에 현재 팩 이름 표시, 범주 칩은 팩의 `categories` + STU + TCH로 동적 생성.
- STU·TCH 문항은 **팩별로 귀속**(A 단원 토론 중 만든 문제는 A 팩에 재투입) — 재투입 루프의 맥락 보존.
- 교사 대시보드: 학생 프로필은 팩 무관 누적 유지(논증 역량은 단원을 관통하는 지표이므로), 히트맵은 현재 발문 기준 유지.
- 상태 구조 변경: `BANK` → `PACKS[packId].items`, `state.currentPackId` 추가. 순환 상태(`cycles`)는 이미 발문 id 단위라 변경 불요.
- 시연 대응: "발문만 바꾸면 어느 단원으로든 확장된다"(10분 버전 8:00 장면)를 **팩 전환 한 번의 클릭**으로 보여줄 수 있게 됨 — 일반화(30점) 배점 직결.

### 3단계 — 타 교과 팩 (명세 9장 4항)
과학 분류 논쟁·사회 가치 논쟁 팩. `consensusMode: "쟁점 정리"` 활성화, 태그 라벨 교체(팩 스키마에 `tagLabels` 선택 필드 추가). 수학 외 교과는 태그 의미가 달라지므로(🔢식 → 📄자료 등) 별도 검토 후 진행.

### AI 발문(교사 백엔드) 확장 — 학운위 승인 반영
- 백엔드 요청에 `packId`·성취기준을 함께 전달해 단원 맥락에 맞는 발문을 생성함.
- 응답 가드(정답 유형 문장 필터링)는 단원 무관 공통 규칙으로 유지: "정답은", "~가 맞다", "~이 옳다" 패턴 차단 후 폴백 카드로 대체.
- 학생 클라이언트 직접 호출 금지 구조는 어떤 확장에서도 유지함.

## 5. 검증 체크리스트 (팩 추가·2단계 구현 시)

- [ ] 명세 하단 점검 문장 6개 전부 통과 (반박 근거 필수 / 정답 미노출 / 개인정보 제로 / localStorage 금지 / 오프라인 완주 / 시작 화면 표기)
- [ ] 새 팩의 모든 문항이 `answerProvided: false`이고 정답 문구가 없는가
- [ ] 예상 주장 2종 중 하나가 '그럴듯한 오개념'인가 (둘 다 정답 계열이면 토론이 안 섬)
- [ ] 팩 전환 후 STU·TCH 재투입이 해당 팩 목록에 나타나는가
- [ ] 팩 전환이 오프라인 상태에서 동작하는가 (팩은 전부 인라인 내장)
